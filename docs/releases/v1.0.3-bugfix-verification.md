## 결론

v1.0.3은 정산·납부 과정의 잔액 처리를 다음과 같이 보완했다.

1. 정산서 작성 화면에서 세대의 미납금 또는 초과납부 환급금을 정산서에 포함하는 버튼이 작동하지 않을 수 있던 원인을 제거했다.
2. 현재 정산서의 미납액보다 큰 입금액도 등록할 수 있다는 정책을 화면에 명시하고, 저장 후 예상되는 미납·완납·초과납부 상태를 입력 중에 보여준다.
3. 초과 입금은 저장을 금지하지 않는다. 실수 방지를 위한 확인을 거친 뒤 세대 누적 입금에 반영하고, 누적 잔액이 음수가 되면 이후 정산서에 환급 항목으로 포함해 납부액을 줄일 수 있다.

초과 입금액은 다른 세대로 이전하거나 자동 분배하지 않는다. 해당 세대의 누적 잔액에만 반영된다.

## 1. 정산서 작성 화면의 잔액 적용 오류

### 관찰된 증상

정산서를 작성할 때 표시되는 `미납금 정산서에 포함` 또는 `환급금 정산서에 포함` 버튼으로 잔액 항목을 정상적으로 추가할 수 없는 사례가 확인됐다.

### 확인된 원인

버튼은 `applyBalance(unitId, balance)`를 호출했지만 함수 내부에서는 호출 인자로 전달되지 않은 전역 `event`의 `target`을 사용해 누른 버튼을 찾았다.

```javascript
const button = event.target;
```

이 구현은 실행 환경이 `event` 전역 값을 암묵적으로 제공한다는 조건에 의존한다. 해당 값이 없거나 다른 이벤트를 가리키면 함수가 오류로 중단되어 버튼 상태와 잔액 적용 흐름이 완결되지 않는다. 정산 데이터나 잔액 계산식의 문제가 아니라 실제 화면의 호출 대상 전달 누락이었다.

### v1.0.3 조치

- 버튼의 인라인 호출에서 실제 버튼인 `this`를 세 번째 인자로 전달한다.
- `applyBalance(unitId, balance, button)`은 전달받은 버튼만 사용한다.
- 버튼이 전달되지 않은 비정상 호출은 데이터 행을 만들기 전에 종료한다.
- 미납금과 초과납부 환급금 버튼에 동일한 호출 규칙을 적용한다.

잔액의 부호에 따른 기존 정책은 유지된다.

| 세대 잔액 | 정산서에 추가되는 항목 | 금액 처리 |
|---:|---|---|
| 양수 | `[이월] 전월 미납금` | 추가 부과 |
| 음수 | `[이월] 전월 초과납부 환급` | 환급, 정산서 금액 차감 |

### 회귀 방지 근거

`tests/test_frontend.py::test_invoice_balance_action_uses_explicit_button_and_payment_allows_credit`가 다음 계약을 확인한다.

- 두 잔액 적용 버튼이 실제 버튼을 `this`로 전달한다.
- 함수가 명시적인 `button` 인자를 받는다.
- 과거 오류 원인인 `const button = event.target`이 정산서 HTML에 남지 않는다.

## 2. 미납액을 초과하는 입금 등록

### 기존 동작과 문제 범위

v1.0.2의 서버 저장 경로도 입금액을 현재 미납액으로 강제 제한하거나 초과분을 잘라내지는 않았다. 초과 입금 경고를 한 번 확인하면 원래 입력한 금액을 저장할 수 있었다.

그러나 화면에는 `현재 미납액`만 표시됐고 초과 입금이 허용된다는 설명, 저장 후 잔액, 이후 정산에서의 처리 방법이 없었다. 경고 문구도 단순히 미납액보다 많다고만 알렸기 때문에 사용자는 초과 금액을 저장할 수 없는 것으로 이해할 수 있었다.

### v1.0.3 조치

- 입금액 입력에는 상한을 두지 않는다. 0원 이상의 원 단위 금액을 입력할 수 있다.
- 현재 상태를 `미납`, `완납`, `초과납부`로 구분해 표시한다.
- 입력 중 `현재 미납액 - 입력액`을 계산해 저장 후 예상 상태를 즉시 보여준다.
- 초과 입금 경고에는 예상 초과납부액과 이후 정산에서 차감할 수 있다는 정책을 표시한다.
- 경고 확인 버튼을 `초과 입금 확인 후 저장`으로 표시해 확인이 거절이 아닌 저장 전 안전 절차임을 구분한다.
- 확인 후에는 사용자가 입력한 전체 금액을 변경하지 않고 저장한다.

미래 날짜 입력과 초과 입금이 동시에 발생하면 두 경고를 함께 확인해야 한다. 이 절차는 금액 상한이 아니라 오입력 방지를 위한 2단계 확인이다.

## 3. 초과 입금과 익월 차감의 데이터 정합성

세대 누적 잔액은 다음 단일 계산식을 사용한다.

```text
세대 누적 잔액 = 이월 항목을 제외한 누적 청구액 - 세대 누적 입금액
```

- 결과가 양수이면 아직 납부할 금액이다.
- 결과가 0이면 완납이다.
- 결과가 음수이면 누적 입금이 실제 청구를 초과한 금액이다.

초과 입금은 해당 입금이 연결된 정산서뿐 아니라 세대의 전체 입금 합계에 포함된다. 다른 정산서의 미납이 남아 있다면 먼저 세대 전체 미납 잔액을 줄이며, 전체 누적 입금이 이월 제외 청구액보다 커진 경우에만 세대 누적 잔액이 음수가 된다.

다음 정산 시 사용자는 음수 잔액을 `전월 초과납부 환급`으로 정산서에 포함할 수 있다. 이 항목은 `is_carryover=true`로 저장되고 배부용 정산서 합계에서는 차감되지만, 세대 누적 청구액에는 다시 포함되지 않는다. 따라서 같은 초과 입금액을 청구와 잔액 양쪽에 중복 계산하지 않는다.

예시는 다음과 같다.

1. 실제 누적 청구액이 100,000원이고 누적 입금액이 120,000원이면 잔액은 -20,000원이다.
2. 다음 달 실제 요금이 80,000원이면 환급 이월 -20,000원을 정산서에 포함해 납부 안내액을 60,000원으로 만들 수 있다.
3. 사용자가 60,000원을 입금하면 이월 제외 누적 청구액 180,000원과 누적 입금액 180,000원이 같아져 세대 누적 잔액은 0원이 된다.

### 회귀 방지 근거

- `tests/test_data_safety_improvements.py::test_future_overpayment_requires_second_confirmation`
  - 초과 입금은 확인 전 저장되지 않는다.
  - 경고가 예상 초과납부 잔액과 이후 정산 차감을 설명한다.
  - 확인 후 원래 금액이 저장된다.
  - 단일 정산서 조건에서 세대 누적 잔액이 음수가 된다.

- `tests/test_carryover.py::test_carryover_flag_survives_round_trip`

## 7. 검증 범위와 한계

- 자동 테스트는 정산서 HTML의 버튼 호출 계약과 서버 저장·잔액 계산을 검증한다. 실제 사용자 환경의 포인터 클릭을 자동화한 데스크톱 UI 종단 테스트는 포함하지 않는다.
- 패키지 스모크 테스트는 Windows와 두 macOS 아키텍처에서 앱 백엔드의 시작·종료와 핵심 HTTP 화면을 검증하지만, 이번 버튼을 실제로 눌러 정산서를 저장하는 과정까지 수행하지 않는다.
- 초과 입금은 자동으로 다음 정산서에 소진되지 않는다. 다음 정산서 작성 시 해당 세대의 환급 잔액을 포함해야 한다.
- 이후 같은 증상이 재발하면 운영체제와 앱 버전, 대상 세대 잔액, 입력 금액, 브라우저 콘솔 오류를 함께 보존해 화면 호출 오류와 데이터 상태를 구분한다.
