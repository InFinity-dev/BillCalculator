## 결론

v1.0.4는 이월 미납이 포함된 정산서의 납부 안내액을 그대로 입금할 때 정상적인 전액 입금이 초과 입금으로 잘못 판정되던 문제를 수정했다.

- 전액 입금과 초과 입금 여부를 선택한 정산서 한 건의 신규 요금이 아니라 해당 세대의 누적 잔액으로 판정한다.
- 입금 한 건으로 이전 정산서에 남은 미납까지 함께 처리할 수 있다.
- 입금 모달에서 이월 포함 정산서 납부 안내액, 선택 정산서에 기입된 입금액과 세대 누적 잔액을 구분해 보여준다.
- 세대 누적 미납액을 실제로 초과한 입금은 기존처럼 확인 후 저장하고, 초과분은 이후 정산에서 차감할 수 있다.

이 변경은 세대 간 금액 이동이나 자동 재분배가 아니다. 모든 입금과 잔액은 선택한 세대 안에서만 계산된다.

## 1. 사용자 증상

납부 관리의 입금 등록 모달에서 이월 미납이 포함된 정산서의 납부 안내액을 입력하거나 `미납액 전액 입력`을 사용해도 저장 대신 초과 입금 확인 메시지가 표시됐다.

대표 재현 조건은 다음과 같다.

| 항목 | 금액 |
|---|---:|
| 이전 정산서 미납 | 17,000원 |
| 최신 정산서 신규 요금 | 8,000원 |
| 최신 정산서에 포함된 이월 미납 | 17,000원 |
| 최신 정산서 납부 안내액 | 25,000원 |
| 세대 누적 미납액 | 25,000원 |

사용자가 배부받은 최신 정산서 금액 25,000원을 입금하면 세대 누적 잔액이 정확히 0원이 되어야 한다. 그러나 v1.0.3은 선택한 최신 정산서의 이월 제외 신규 요금 8,000원과 입금액을 비교해 17,000원 초과 입금으로 판정했다.

## 2. 확인된 근본 원인

잔액 계산에는 의도적으로 두 종류의 금액이 존재한다.

1. `FinalInvoice.total_amount`: 사용자가 받은 정산서에 표시되는 납부 안내액으로, 전월 미납 또는 초과납부 환급 이월을 포함한다.
2. `balance.invoice_billed_amount()`: 세대 누적 잔액에 새로 더할 실제 청구액으로, 같은 잔액을 두 번 계산하지 않도록 이월 항목을 제외한다.

v1.0.3의 세대 요약은 모든 정산서의 이월 제외 청구액과 모든 입금액을 합산해 올바른 누적 잔액을 계산했다. 반면 입금 모달의 전액 입력과 서버의 초과 입금 경고는 선택한 정산서 한 건의 이월 제외 청구액만 기준으로 사용했다.

따라서 세대 누적 잔액은 25,000원이지만 선택 정산서 기준 잔액은 8,000원인 서로 다른 범위가 만들어졌다. 정산서 납부 안내액 25,000원을 입력하면 데이터상 정상적인 누적 미납 전액 입금인데도 모달과 서버가 초과 입금으로 분류했다.

## 3. v1.0.4 조치

### 3.1 서버 판정 기준 통일

`balance.unit_outstanding_before_payment()`를 추가해 입금 직전의 세대 누적 잔액을 단일 기준으로 계산한다.

```text
입금 전 세대 누적 잔액 = 이월 제외 전체 청구액 - 세대 전체 입금액
```

- 신규 입금은 현재 세대 누적 잔액과 비교한다.
- 입금 수정은 기존 입금액이 누적 입금에 이미 포함돼 있으므로 해당 금액을 잠시 되돌린 뒤 새 금액과 비교한다.
- 서버의 초과 입금 경고도 이 값을 사용한다.
- 입금액이 세대 누적 미납액과 같으면 추가 확인 없이 저장한다.
- 세대 누적 미납액보다 큰 경우에만 예상 초과납부액을 표시하고 한 번 더 확인한다.

입금 기록은 사용자가 모달을 연 정산서에 연결되지만, 세대 누적 잔액은 기존 정책대로 해당 세대의 모든 정산서와 모든 입금을 합산한다.

### 3.2 입금 모달의 금액 범위 명시

정산서별 이력 응답에 `payable_amount`를 추가했다. 이 값은 `FinalInvoice.total_amount`를 그대로 사용하므로 이월 부과·환급을 포함한 배부 정산서 금액과 일치한다.

입금 모달은 다음 세 값을 구분한다.

| 화면 표시 | 의미 |
|---|---|
| 정산서 납부 안내액 | 선택한 정산서의 이월 포함 최종 금액 |
| 이 정산서 기입금액 | 선택한 정산서에 연결해 이미 기록한 입금 합계 |
| 세대 누적 잔액 | 이전·현재 정산서를 모두 합산한 실제 미납 또는 초과납부 잔액 |

`세대 미납액 전액 입력` 버튼과 입력 중 예상 잔액도 세대 누적 잔액을 사용한다. 따라서 어느 정산서의 입금 등록 버튼에서 시작해도 해당 세대의 이전 미납까지 한 번에 입력할 수 있다.

## 4. 회귀 방지 근거

`tests/test_payment_management.py::test_full_unit_outstanding_can_be_paid_from_latest_invoice`가 실제 오류 조건을 고정한다.

1. 첫 정산서에 17,000원 미납을 만든다.
2. 신규 요금 8,000원과 이월 미납 17,000원을 합친 총액 25,000원의 다음 정산서를 만든다.
3. 이력 API가 신규 청구액 `billed_amount=8,000`과 이월 포함 `payable_amount=25,000`을 구분하는지 확인한다.
4. 세대 누적 잔액이 25,000원인지 확인한다.
5. 최신 정산서에 25,000원 입금을 등록한다.
6. 초과 입금 확인 없이 저장되고 세대 누적 잔액이 0원이 되는지 확인한다.

`tests/test_frontend.py`는 입금 모달이 세대 누적 잔액을 사용하고, 전액 입력 버튼과 설명이 이전 정산서 미납까지 포함하는지 확인한다.

기존 `tests/test_data_safety_improvements.py`는 세대 누적 미납보다 큰 금액의 2단계 확인과 저장 후 음수 잔액 동작을 계속 검증한다. 따라서 정상적인 누적 미납 전액 입금은 바로 저장하고 실제 초과 입금은 확인 후 저장하는 두 경로가 함께 보존된다.

## 8. 데이터·호환성 영향과 검증 한계

- DB 스키마 변경이나 마이그레이션은 없다. 기존 정산서와 입금 데이터는 그대로 사용한다.
- 기존 이월 중복계상 방지 규칙은 변경하지 않는다. 이월은 정산서 표시 총액에는 포함되지만 누적 청구액에는 포함되지 않는다.
- 입금은 다른 세대의 미납에 배분되지 않는다. 선택한 세대의 누적 잔액만 줄인다.
- 자동 테스트는 Flask API의 실제 저장과 렌더링된 모달 스크립트 계약을 검증한다. 데스크톱 창에서 버튼을 실제 클릭하는 UI 종단 테스트는 포함하지 않는다.
- 패키지 스모크 테스트는 세 운영체제에서 백엔드 시작·핵심 화면·튜토리얼 데이터·안전 종료를 검사하지만 운영 데이터 사본을 사용한 입금 조작은 수행하지 않는다.
