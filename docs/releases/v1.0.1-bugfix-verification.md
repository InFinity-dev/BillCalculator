# v1.0.1 버그 수정 검증 기록

> 후속 확인(2026-11-14): v1.0.1의 정적 자원 주소 안정화만으로는 Windows 튜토리얼 5단계 요금계산 화면의 스타일 누락을 완전히 막지 못했다. 아래 2번의 “해결” 평가는 **부분 개선**으로 정정한다. 후속 구현은 튜토리얼 CSS·필수 JavaScript를 각 HTML 응답에 직접 포함하고, 패키지 스모크 테스트가 실제 계산 화면의 내장 자원을 검사하도록 변경했다.

- 검증일: 2026-11-14
- 비교 범위: `v1.0.0` (`f448b99`) → `v1.0.1` (`172c498`)
- 대상: Windows 패키지의 실제 화면 튜토리얼 진행 상태와 정적 자원 로딩
- 최종 배포 검증: GitHub Actions 실행 [43456900541](https://github.com/InFinity-dev/BillCalculator/actions/runs/43456900541)

## 결론

v1.0.1에 게시한 첫 번째 문구는 사용자가 겪은 증상과 해결 범위를 올바르게 설명한다. 두 번째 문구는 실제 변경 범위를 **Windows 앱의 튜토리얼 화면**으로 한정해야 하며, 후속 재현 결과 완전한 해결이 아니라 발생 경로 일부를 줄인 부분 개선이었다.

권장 릴리즈 문구는 다음과 같다.

- Windows 앱의 튜토리얼에서 화면을 이동하면 현재 단계가 처음으로 돌아갈 수 있던 문제를 수정했습니다.
- Windows 앱의 튜토리얼 정적 자원 주소를 안정화해 화면 이동 뒤 스타일 누락 가능성을 줄였습니다. 다만 요금계산 단계의 재발은 후속 릴리즈에서 수정합니다.

## 1. 튜토리얼 진행도가 처음으로 돌아가는 문제

### 확인된 증상

Windows 앱에서 튜토리얼을 진행하다가 계산 내역의 `상세`처럼 다른 주소로 이동하는 실제 버튼을 누르면, 다음 화면에서 현재 단계 대신 첫 단계가 열릴 수 있었다.

### 확인된 원인

v1.0.0은 진행 단계를 브라우저의 `localStorage`에 주로 의존했다. 일부 링크 이동에는 `_tutorial_step` 쿼리가 붙었지만, 다음 단계 이동과 현재 화면 교정 등 모든 프로그램 이동이 같은 방식으로 단계를 전달하지는 않았다. 따라서 Windows 패키지에서 화면 전환 뒤 저장값을 읽지 못하거나 새 문서가 전달받은 단계가 없으면 `readStep()`의 기본값인 0으로 복귀할 수 있었다.

여기서 확정할 수 있는 원인은 **단계 상태의 단일 저장 경로 의존과 이동 경로별 전달 방식의 불일치**다. 당시 사용자 PC의 Electron 저장소 로그가 남아 있지 않으므로, Windows에서 `localStorage` 읽기가 실패한 더 하위 원인까지 하나로 단정하지 않는다.

### v1.0.1 조치 — 부분 개선

커밋 `a703f5f`에서 다음을 적용했다.

1. 튜토리얼 실행 ID별 진행 단계를 URL의 `_tutorial_step`, 호스트 쿠키, `localStorage`에 함께 기록한다.
2. URL → 쿠키 → `localStorage` 순서로 유효한 단계를 복구한다.
3. 저장소 접근이 제한되어도 튜토리얼이 중단되지 않도록 모든 저장소 접근을 안전 함수로 감쌌다.
4. 다음 단계 이동, 실제 링크 클릭, 잘못된 화면에서의 자동 교정을 모두 `navigateWithStep()`으로 통일해 목적지 URL에 현재 단계를 명시한다.
5. 실행 ID를 키에 포함해 이전 연습의 단계가 새 연습으로 섞이지 않게 했다.

### 당시 검증과 누락 범위

- `tests/test_tutorial.py`가 URL 파라미터·실행별 쿠키·안전한 저장소 함수·공통 이동 함수의 존재와 사용을 고정한다.
- 최종 패키지 스모크 테스트가 실제 PyInstaller 실행 파일로 본 서버에서 튜토리얼 전용 서버까지 이동한다.
- 최종 전체 테스트 318개와 Windows x64 패키지 스모크 테스트가 통과했다.

## 2. 화면 이동 뒤 스타일이 적용되지 않는 문제

### 확인된 증상

Windows 앱의 튜토리얼에서 화면을 이동할 때 HTML 본문은 보이지만 CSS가 적용되지 않은 것처럼 보이는 화면이 간헐적으로 나타났다.

### 확인된 구조적 원인

v1.0.0의 튜토리얼 HTML은 실행할 때마다 임의 포트로 생성되는 전용 Flask 서버가 제공했고, CSS와 JavaScript도 그 일회성 서버의 상대 주소(`/static/...`)에서 불러왔다. 정적 자원 주소에 앱 버전도 없었다. 이 구조에서는 전용 프로세스의 시작·수명 문제 또는 Electron에 남은 이전 자원 캐시의 혼용이 생기면 HTML과 정적 자원의 가용성·버전이 달라질 수 있었다.

당시 사용자 PC의 Network/Console 기록이 없으므로 “특정 CSS 요청 한 건이 어떤 오류 코드로 실패했다”까지 재구성할 수는 없다. 따라서 **일회성 튜토리얼 서버와 버전 없는 정적 자원 주소가 확인된 취약점**이며, 캐시 또는 프로세스 중 어느 하나만이 원인이었다고 단정하지 않는다.

### 해결 방식

커밋 `a703f5f`에서 다음을 적용했다.

1. `asset_url()`을 추가해 튜토리얼 HTML의 CSS·JavaScript를 수명이 긴 본 앱 서버에서 불러오도록 했다.
2. 모든 정적 자원 주소에 앱 버전 쿼리(`?v=1.0.1`)를 붙여 이전 패키지의 캐시와 새 HTML이 섞이지 않게 했다.
3. 공통 레이아웃뿐 아니라 계산·내역·정산·인쇄·납부·설정 등 튜토리얼이 방문하는 템플릿의 정적 자원 주소를 같은 방식으로 통일했다.

### 회귀 방지 근거

- `tests/test_tutorial.py`가 튜토리얼 HTML에 본 앱 주소와 앱 버전이 포함된 CSS·JavaScript URL이 생성되는지 확인한다.
- `scripts/smoke_test_desktop_backend.py`가 패키징된 백엔드로 튜토리얼을 실제 시작한 뒤, HTML에 포함된 핵심 CSS·JavaScript 세 파일을 본 서버에서 직접 요청해 HTTP 200과 비어 있지 않은 본문을 확인한다.
- 최종 Windows x64 작업의 `Smoke-test packaged backend` 단계가 통과했다.
- 그러나 이 검증은 실제 5단계 `/calculator` HTML과 해당 화면이 크게 의존하는 `utilities.css`, `calculator.css`를 확인하지 않았다. 이 누락 때문에 v1.0.1에서도 해당 단계의 스타일 누락이 재발할 수 있었다.

### 후속 해결

- 튜토리얼 화면에서는 공통 CSS, 유틸리티 CSS, 화면별 CSS와 필수 JavaScript를 HTML 응답에 직접 포함한다.
- 일반 업무 화면만 앱 버전이 붙은 외부 정적 파일과 브라우저 캐시를 사용한다.
- 패키지 스모크 테스트가 `/calculator?_tutorial_step=4`를 직접 열어 `app.css`, `utilities.css`, `tutorial_overlay.css`, `calculator.css`, `app.js`, `tutorial_overlay.js`의 내장 여부를 확인한다.

## 3. 강화된 검증에서 추가로 발견한 Windows 패키지 문제

아래 항목은 두 사용자 증상을 재현한 직접 증거가 아니라, v1.0.1의 패키지 경로를 실제로 검사하면서 발견해 함께 제거한 하위 프로세스 안정성 문제다. 튜토리얼 시작·데모 생성·종료에는 직접 영향을 주지만, 진행도 초기화와 스타일 누락을 모두 설명하는 하나의 원인은 아니다.

| 검증 실행 | 확인된 실패 | 조치 |
|---|---|---|
| [43451034687](https://github.com/InFinity-dev/BillCalculator/actions/runs/43451034687) | Windows 패키지에서 튜토리얼 전용 서버로 이동하지 못함 | PyInstaller onefile 하위 실행을 별도 압축 해제 인스턴스로 시작 |

관련 수정 커밋은 `c832dc3`, `f7a1faf`, `d797629`, `6483039`, `172c498`이다.

PyInstaller 6.9 이상에서 독립적으로 살아야 하는 `onefile` 자기 실행에는 `PYINSTALLER_RESET_ENVIRONMENT=1`이 필요하다는 점은 [PyInstaller 공식 문서](https://pyinstaller.org/en/stable/common-issues-and-pitfalls.html#using-sys-executable-to-spawn-subprocesses-that-outlive-the-application-process)와 일치한다. 또한 frozen 앱은 격리된 Python 인터프리터를 사용하므로 `PYTHONIOENCODING` 환경 변수만으로 해결됐다고 볼 수 없다. Windows CI에서 효과가 확인된 핵심 UTF-8 조치는 `sys.stdout`·`sys.stderr`를 직접 재설정한 커밋 `6483039`다.

## 검증 범위의 한계

- 최초 사용자 PC에서 발생한 순간의 Electron Network/Console 로그는 보존되지 않았다.
- 따라서 공개 릴리즈 노트는 관찰된 증상과 검증된 해결 범위만 표현한다.
- “브라우저 캐시만이 원인이었다” 또는 “CSS 파일 서버가 항상 종료되었다”와 같은 단일 원인 표현은 사용하지 않는다.
- 재발 방지는 정적 코드 확인만이 아니라 Windows에서 만든 실제 패키지의 튜토리얼 시작·정적 자원 응답·종료까지 검사하는 스모크 테스트로 보강했다.
