## 결론

v1.0.2는 Windows 앱 튜토리얼에서 확인된 두 가지 진행 차단 문제를 수정했다.

1. 튜토리얼 서버를 열기 전에 전용 DB의 실제 층·세대·요금 데이터가 완전한지 검사하고, 생성기가 소유한 불완전한 연습 DB는 초기 상태로 다시 만든다.
2. 튜토리얼 화면에 필요한 CSS와 필수 JavaScript를 HTML 응답에 직접 포함한다. 특히 5단계 요금 계산 화면을 패키징된 백엔드로 직접 열어 화면별 스타일 포함 여부까지 검사한다.

실제 사용자 업무 DB와 튜토리얼 DB의 격리 정책, 튜토리얼 재진입 시 데모 데이터를 초기화하는 정책은 유지된다. 일반 업무 화면은 기존과 같이 버전이 붙은 외부 정적 파일과 브라우저 캐시를 사용한다.

## 1. 데모 데이터 없이 튜토리얼이 시작되는 문제

### 관찰된 증상

Windows 설치본에서 튜토리얼은 시작되지만 연습용 층·세대·요금 데이터가 없어 다음 동작을 수행할 수 없는 사례가 확인됐다. 화면 자체는 열리므로 사용자는 튜토리얼 중간까지 이동한 뒤에야 진행 불가능 상태를 알 수 있었다.

### 확인된 구조적 원인

v1.0.1까지의 준비 판정은 튜토리얼 DB의 생성기 소유 정보와 시나리오 버전을 중심으로 확인했다. 그러나 실제 테이블에 필요한 층·세대·미정산 계산서가 모두 존재하는지는 시작 전에 검증하지 않았다. 생성 도중 중단되거나 행이 누락된 DB라도 소유 정보와 버전만 남아 있으면 재사용될 수 있는 틈이 있었다.

또한 당시 패키지 스모크 테스트는 튜토리얼 서버로 이동하고 정적 자원을 받을 수 있는지 확인했지만, 연습 DB의 실제 행 구성까지 확인하지 않았다.

원 사용자 PC에서 문제가 발생한 순간의 백엔드 로그와 DB 사본은 보존되지 않았다. 따라서 특정 파일 생성 실패나 프로세스 종료 시점을 단일 직접 원인으로 단정하지 않고, 재현 가능한 **준비 완료 판정의 검증 공백**을 원인 범위로 기록한다.

### v1.0.2 조치

`tutorial_service.inspect_tutorial_database()`가 다음 시나리오 실체를 검사한다.

- 층: 지하 1층, 1층, 2층
- 세대: 총 8세대
- 아직 정산서에 포함되지 않은 전기 계산서: 2026년 9월 3개 층, 2026년 10월 1·2층의 총 5건
- 아직 정산서에 포함되지 않은 수도 계산서: 2026년 10월 348,000원, 6개 상세 항목의 1건
- 튜토리얼 준비 완료 표식과 시나리오 버전 3

검사 결과가 불완전하면 다음과 같이 처리한다.

1. BillCalculator 튜토리얼 생성기가 소유한 DB만 삭제하고 동일한 기본 시나리오로 다시 만든다.
2. 새 DB를 다시 엄격히 검사한다.
3. 새 DB도 유효하지 않으면 파일을 제거하고 시작을 실패 처리한다. 빈 데이터로 튜토리얼을 계속 열지 않는다.
4. `/tutorial/health`는 데이터 건수와 `dataset_ready`를 반환하고, 불완전한 데이터에는 HTTP 503을 반환한다.
5. 데스크톱 런타임은 단순 HTTP 200이 아니라 `dataset_ready=true`를 확인한 뒤에만 튜토리얼 창을 연다.

이 교체 정책은 실행별 `tutorial_sessions` 아래에서 생성기 소유가 확인된 연습 DB에만 적용된다. 사용자의 업무 DB를 자동 삭제하거나 데모 데이터로 덮어쓰지 않는다.

### 회귀 방지 근거

  - 층 행이 삭제된 생성기 소유 DB를 감지하고 정상 시나리오로 복구하는지 확인한다.
  - 빈 DB의 상태 확인이 503, 완전한 데모 DB가 200과 정확한 건수를 반환하는지 확인한다.

## 2. 튜토리얼 5단계 요금 계산 화면의 스타일 누락

### 관찰된 증상

v1.0.1 Windows 설치본에서 튜토리얼 5단계 `요금 계산` 화면이 CSS가 적용되지 않은 원시 HTML처럼 보이는 문제가 다시 확인됐다.

### v1.0.1 조치가 충분하지 않았던 이유

v1.0.1은 튜토리얼 CSS·JavaScript 주소를 수명이 긴 본 앱 서버로 옮기고 앱 버전 쿼리를 추가했다. 이 변경은 일회성 튜토리얼 서버와 오래된 캐시가 섞일 가능성을 줄였지만, HTML과 별도로 여러 정적 파일을 요청해야 한다는 구조는 남아 있었다.

요금 계산 화면은 공통 `app.css` 외에도 `utilities.css`와 `css/pages/calculator.css`에 크게 의존한다. 당시 패키지 스모크 테스트는 초기 튜토리얼 HTML의 `app.css`, `tutorial_overlay.css`, `tutorial_overlay.js`만 확인했고, 실제 `/calculator` 페이지와 두 계산 화면 스타일 파일은 검사하지 않았다. 따라서 초기 화면 검증이 통과해도 계산 화면만 불완전할 수 있었다.

당시 Windows 클라이언트의 Electron Network/Console 기록은 남아 있지 않다. 특정 요청의 실패 코드나 캐시 상태는 단정하지 않으며, 확인된 원인은 **튜토리얼의 별도 정적 파일 요청 의존성**과 **계산 화면 패키지 검증 누락**이다.

### v1.0.2 조치

`stylesheet_asset()`와 `script_asset()`을 추가해 렌더링 방식을 실행 모드별로 나눴다.

- 튜토리얼 모드: 배포 패키지에 포함된 CSS와 필수 JavaScript를 읽어 각 HTML 응답의 `<style data-inline-stylesheet>`와 `<script data-inline-script>`에 직접 포함한다.
- 일반 업무 모드: 기존처럼 버전이 붙은 `/static/...` 주소를 사용해 캐시 효율을 유지한다.

공통 레이아웃과 튜토리얼이 방문하는 요금 계산, 계산 내역, 정산서, 인쇄, 납부 관리, 설정 템플릿에 같은 정책을 적용했다. 정적 파일 경로는 앱의 `static` 디렉터리 내부로 제한하고, 읽기 실패 시 불완전한 HTML을 조용히 반환하지 않고 오류로 처리한다.

### 회귀 방지 근거

- `tests/test_tutorial.py`가 튜토리얼 HTML에 다음 자원이 내장되고, 계산 화면에 외부 스타일시트 링크가 남지 않는지 확인한다.
  - `css/app.css`
  - `css/utilities.css`
  - `css/tutorial_overlay.css`
  - `css/pages/calculator.css`
  - `js/app.js`
  - `js/tutorial_overlay.js`
- 같은 테스트가 일반 업무 화면에는 기존 정적 파일 주소가 유지되는지 확인한다.
- `scripts/smoke_test_desktop_backend.py`가 패키징된 백엔드의 `/calculator?_tutorial_step=4`를 직접 열어 위 자원, 계량기 입력 대상과 외부 `rel="stylesheet"` 부재를 검사한다.

## 3. Windows 패키지 하위 프로세스·UTF-8 문제 재검증

이 항목들은 추측으로 추가한 예방 조치가 아니라 Windows 패키지 CI에서 실제로 발견된 문제다. 다만 진행도 초기화, 스타일 누락과 모두 같은 원인이라고 해석하지 않는다.

macOS 검증에서는 확인되지 않고 Windows에서 먼저 드러난 이유의 상세 분석은 [Windows·macOS 플랫폼 차이 분석](windows-macos-tutorial-difference.md)을 참고한다.

### 3.1 PyInstaller `onefile` 하위 프로세스

BillCalculator 데스크톱 백엔드는 PyInstaller `6.22.3`의 `onefile` 실행파일이다. 패키지 상태에서는 같은 실행파일을 `sys.executable`로 다시 실행해 데모 DB 생성(`seed-demo`)과 튜토리얼 서버(`serve`)를 시작한다.

PyInstaller 6.9 이상은 같은 실행파일로 만든 자식 프로세스를 기본적으로 현재 번들의 작업 프로세스로 취급한다. 부모와 독립적으로 실행될 프로세스에는 `PYINSTALLER_RESET_ENVIRONMENT=1`을 지정해 새 최상위 인스턴스로 시작해야 한다. 이는 [PyInstaller 공식 문서](https://pyinstaller.org/en/stable/common-issues-and-pitfalls.html#using-sys-executable-to-spawn-subprocesses-that-outlive-the-application-process)에 명시된 방식이다.

- [실행 43451034687](https://github.com/InFinity-dev/BillCalculator/actions/runs/43451034687): Windows 패키지에서 튜토리얼 전용 서버로 이동하지 못했다.
- 커밋 `c832dc3`은 튜토리얼 서버 자식에 독립 실행 환경을 적용했다.
- [실행 43452266549](https://github.com/InFinity-dev/BillCalculator/actions/runs/43452266549): 서버 자식만 변경한 뒤에도 튜토리얼 전용 서버 이동 실패가 계속됐다. 이 로그만으로 남은 실패 지점을 특정할 수 없어 독립 실행 적용 범위를 데모 생성 자식까지 확대하고 자식 로그를 보존했다.
- 커밋 `f7a1faf`은 데모 생성 자식에도 독립 실행 환경을 적용하고 자식 로그를 보존했다. 이후 검증은 다음 단계인 한국어 출력 오류를 정확히 노출했다.

공식 동작 정의와 CI 진행 순서는 기존 프로세스 모델에 실제 결함이 있었음을 뒷받침한다. 다만 최초 실행의 로그는 “튜토리얼 서버로 이동하지 못함”까지만 남아 있어, 그 한 번의 실패가 압축 해제 환경 재사용 하나만으로 발생했다고 단정하지 않는다.

### 3.2 Windows `cp1252`와 UTF-8 표준 출력

[실행 43453327570](https://github.com/InFinity-dev/BillCalculator/actions/runs/43453327570)의 Windows 로그에는 데모 DB 생성 완료 문구를 출력하는 `scripts/demo.py`에서 다음 예외가 기록됐다.

```text
encodings\cp1252.py
UnicodeEncodeError: 'charmap' codec can't encode characters
```

따라서 한국어 출력 문제가 실제였다는 점은 확정할 수 있다. 다만 해결 과정은 두 단계로 구분해야 한다.

1. 커밋 `d797629`에서 `PYTHONIOENCODING=utf-8`과 자식 출력 디코딩의 `encoding="utf-8"`을 지정했다.
2. [실행 43454348932](https://github.com/InFinity-dev/BillCalculator/actions/runs/43454348932)에서도 동일한 `cp1252` 오류가 재현됐다. PyInstaller frozen 앱은 격리된 내장 인터프리터를 사용해 Python 인터프리터용 환경 변수를 일반 Python 실행과 동일하게 처리하지 않을 수 있다. [PyInstaller 환경 변수 문서](https://pyinstaller.org/en/stable/advanced-topics.html#environment-variables-used-by-frozen-applications)도 이 제한을 설명한다.
3. 커밋 `6483039`에서 백엔드 시작 직후 `sys.stdout`과 `sys.stderr`에 `reconfigure(encoding="utf-8", errors="backslashreplace")`를 직접 적용했다. 이는 Python의 [표준 스트림 재설정 API](https://docs.python.org/3/library/io.html#io.TextIOWrapper.reconfigure)를 사용한 조치다.
4. 다음 Windows 실행은 데모 생성과 튜토리얼 시작을 통과하고 종료 단계까지 진행했다.

따라서 `PYTHONIOENCODING`만으로 해결됐다는 표현은 정확하지 않다. 현재 환경 변수는 보조 방어이며, 패키징된 실행파일에서 효과가 확인된 핵심 조치는 표준 스트림의 명시적 UTF-8 재설정이다.

### 3.3 Windows 프로세스 트리 종료와 SQLite 잠금

[실행 43455317105](https://github.com/InFinity-dev/BillCalculator/actions/runs/43455317105)는 백엔드 종료가 10초 안에 끝나지 않았고, 튜토리얼 DB를 잡고 있는 프로세스가 남아 `WinError 32`로 파일 삭제가 실패했다.

단일 `terminate()`는 PyInstaller 부트로더와 실제 서버를 포함한 Windows 프로세스 트리 전체를 종료하지 못했다. 커밋 `172c498`에서 Windows 종료를 `taskkill /PID ... /T /F`로 변경했고, [최종 실행 43456900541](https://github.com/InFinity-dev/BillCalculator/actions/runs/43456900541)의 Windows x64 패키지 스모크 테스트가 통과했다.

이 문제는 종료와 DB 잠금 해제의 실제 원인이지만, 이미 열린 튜토리얼의 진행도 초기화나 계산 화면 스타일 누락을 설명하는 직접 원인은 아니다.

## 7. 공개 릴리즈 노트와 기술적 표현

사용자용 릴리즈 노트는 다음 두 수정으로 요약됐다.

- Windows 앱에서 연습용 층·세대·요금 데이터가 없어 튜토리얼을 진행할 수 없던 문제를 수정했다. 시작 전에 실제 데이터 구성을 확인하고 불완전한 연습 데이터는 다시 만든다.
- Windows 앱의 튜토리얼 5단계 요금 계산 화면에서 스타일이 빠질 수 있던 문제를 수정했다. 필요한 화면 스타일과 동작 파일을 HTML에 포함해 페이지 이동과 별도 정적 파일 요청의 영향을 제거했다.

첫 문장의 “자동으로 다시 만든다”는 생성기가 소유한 튜토리얼 전용 DB에만 해당한다. 두 번째 문장의 해결 근거는 외부 자원 요청 제거와 실제 계산 화면 패키지 검사다. “Windows 캐시만이 원인이었다”처럼 보존되지 않은 현장 로그가 필요한 단일 원인 표현은 사용하지 않는다.

## 8. 검증 한계와 후속 진단 기준

- 최초 문제가 발생한 Windows PC의 백엔드 로그, Electron Network/Console 기록과 해당 튜토리얼 DB는 보존되지 않았다.
- 따라서 한 번의 실제 발생을 만든 운영체제·파일·요청 수준의 단일 원인은 재구성할 수 없다.
- v1.0.2는 불완전한 데이터가 준비 완료로 통과하는 경로를 차단하고, 튜토리얼 HTML이 화면 CSS를 별도 요청하는 경로를 제거했다.
- 같은 증상이 다시 발생하면 앱 버전, 튜토리얼 상태 응답, 백엔드 로그, 해당 화면 HTML과 Electron Network/Console 기록을 함께 보존해 이번 구조적 원인과 구분한다.
